# Assessment RINH

## 1. Название проекта
**Assessment RINH** — веб-система для ведения оценочных материалов в контексте образовательных программ, дисциплин и компетенций.

## 2. Краткое описание проекта
Это Django-приложение с PostgreSQL, где методист/преподаватель может:
- вести справочники и структуру образовательных программ;
- формировать матрицу «дисциплина учебного плана -> компетенция»;
- создавать и редактировать оценочные задания разных типов;
- формировать отчеты по покрытию и структуре заданий;
- выгружать печатные материалы в `.docx`;
- импортировать программу из `.plx`.

## 3. Назначение системы
Система предназначена для управления **оценочными материалами учебного процесса** в связке с реальной структурой ОПОП:
- уровень образования -> направление -> профиль -> образовательная программа;
- дисциплины учебного плана;
- компетенции программы;
- задания, проверяющие конкретные компетенции по конкретным дисциплинам учебного плана.

## 4. Для кого предназначена система
- методисты и сотрудники учебно-методических подразделений;
- преподаватели, разрабатывающие оценочные материалы;
- администраторы, поддерживающие справочники и структуру программ.

## 5. Какие задачи решает система
- централизует хранение заданий в привязке к учебным планам;
- исключает разрыв между дисциплинами, компетенциями и заданиями;
- упрощает подготовку печатных комплектов оценочных материалов;
- позволяет анализировать покрытие компетенций и распределение заданий.

## 6. Основные возможности
- CRUD через сайт (не только `/admin`) для ключевых сущностей:
  - кафедры, преподаватели;
  - направления, профили, образовательные программы;
  - дисциплины, дисциплины учебного плана;
  - компетенции, матрица дисциплина-компетенция;
  - оценочные задания.
- Создание/редактирование задания с inline-строками (`assessment_item_row`) и валидацией по типу.
- Автопоиск (autocomplete) для длинных справочников и связей.
- Импорт образовательной программы из `.plx` с проверкой конфликта и подтвержденной заменой.
- Экспорт в Word по фильтрам.
- Отчеты по типам заданий, программам, дисциплинам и покрытию компетенций.

## 7. Архитектура проекта
Проект построен как набор Django-приложений вокруг предметного ядра:

- `core` — справочники, главная страница, базовые CRUD-классы, lookup API для автопоиска.
- `teachers` — кафедры/преподаватели.
- `programs` — направления/профили/программы + сервисный импорт `.plx`.
- `disciplines` — справочник дисциплин и связи с программами.
- `competencies` — компетенции программы и матрица дисциплина-компетенция.
- `assessment` — задания и строки заданий, ключевая предметная логика.
- `reports` — агрегированные отчеты.
- `export` — формирование `.docx`-документа.

### Почему это не «обычный сайт с тестами»
Система хранит задания не изолированно, а как часть образовательной модели:
- задание связано не просто с дисциплиной, а с `program_discipline` (дисциплина **конкретной** образовательной программы);
- задание связано с компетенцией этой же программы;
- доступность компетенции для задания ограничивается матрицей `discipline_competence`.

Это делает данные пригодными для методической и аккредитационной работы, а не только для проведения теста.

## 8. Структура приложений Django

### `core`
- **Назначение:** базовые справочники и общая инфраструктура UI.
- **Модели:** `EducationLevel`, `CompetenceType`, `AssessmentItemType`, `AcademicDegree`, `AcademicTitle`.
- **Формы:** простые `ModelForm` + вспомогательные функции autocomplete (`apply_autocomplete_attrs`, `autocomplete_queryset`).
- **Views:** `HomeView`, CRUD справочников, `lookup_options`.
- **URLs:** `/core/...`, `/core/lookup/`.
- **Шаблоны:** главная страница использует `templates/home.html`, типовые CRUD-шаблоны — `templates/common/*`.
- **Связи:** lookup используется практически всеми другими приложениями.

### `teachers`
- **Назначение:** управление кафедрами и преподавателями.
- **Модели:** `Department`, `Teacher`.
- **Формы:** `DepartmentForm`, `TeacherForm` (в т.ч. ограничение выбора заведующего по кафедре).
- **Views:** dashboard + CRUD.
- **URLs:** `/teachers/...`.
- **Шаблоны:** `templates/teachers/dashboard.html` + `templates/common/*`.
- **Связи:** `Department` используется в `programs.EducationalProgram`.

### `programs`
- **Назначение:** иерархия программ и импорт из `.plx`.
- **Модели:** `TrainingDirection`, `ProgramProfile`, `EducationalProgram`.
- **Формы:** формы CRUD + `PlxImportUploadForm`.
- **Views:** dashboard с таблицами + CRUD + сценарий импорта/подтверждения замены.
- **URLs:** `/programs/...`.
- **Шаблоны:** `templates/programs/dashboard.html` + `templates/common/*`.
- **Сервисы:** `programs/services/*` (`plx_parser`, `plx_mapping`, `plx_import_service`, `program_replace_service` и др.).
- **Связи:** центральный узел для дисциплин, компетенций, заданий.

### `disciplines`
- **Назначение:** справочник дисциплин и управление `ProgramDiscipline`.
- **Модели:** `Discipline`, `ProgramDiscipline`.
- **Формы:** CRUD + специализированная `ProgramDisciplineManageForm`.
- **Views:** основной экран управления дисциплинами выбранной программы + CRUD и endpoint `by-program`.
- **URLs:** `/disciplines/...`.
- **Шаблоны:** `templates/disciplines/manage_program_disciplines.html`, `templates/disciplines/list.html`.
- **Связи:** `ProgramDiscipline` используется в `assessment` и `competencies`.

### `competencies`
- **Назначение:** компетенции программ и матрица дисциплина-компетенция.
- **Модели:** `Competence`, `DisciplineCompetence`.
- **Формы:** ограничения по программе и дисциплине.
- **Views:** dashboard + CRUD + endpoint `by-program-discipline`.
- **URLs:** `/competencies/...`.
- **Шаблоны:** `templates/competencies/list.html`.
- **Связи:** `Competence` используется в заданиях; `DisciplineCompetence` ограничивает допустимые связи в `assessment`.

### `assessment`
- **Назначение:** управление оценочными заданиями.
- **Модели:** `AssessmentItem`, `AssessmentItemRow`.
- **Формы:** `AssessmentItemForm`, `AssessmentItemRowForm`, formset-валидация по типу.
- **Views:** список с фильтрами, карточка, create/update/delete.
- **URLs:** `/assessment/...`.
- **Шаблоны:** `templates/assessment/list.html`, `form.html`, `detail.html`.
- **Сервисы:** `assessment/services.py` (нормализация типов, UI-названия, разбор строк, человекочитаемые ошибки БД).
- **Связи:** использует `ProgramDiscipline`, `Competence`, `AssessmentItemType`.

### `reports`
- **Назначение:** аналитические отчеты.
- **Модели:** собственных предметных моделей нет (`reports/models.py` пустой).
- **Формы:** `ReportFilterForm`.
- **Views:** `ReportsDashboardView` с `annotate/Count`.
- **URLs:** `/reports/`.
- **Шаблоны:** `templates/reports/report.html`.
- **Связи:** строит отчеты по моделям `assessment`, `competencies`, `disciplines`, `programs`.

### `export`
- **Назначение:** экспорт оценочных материалов в Word.
- **Модели:** собственных предметных моделей нет (`export/models.py` пустой).
- **Формы:** `WordExportForm`.
- **Views:** `WordExportView`.
- **URLs:** `/export/word/` (и редирект `/export/`).
- **Шаблоны:** `templates/export/word.html`, макет `templates/export/maket.docx`.
- **Сервисы:** `export/services.py`.
- **Связи:** использует задания, дисциплины, компетенции, типы заданий.

## 9. Описание основных моделей и сущностей

### Учебная структура
- `EducationLevel` -> `TrainingDirection` -> `ProgramProfile` -> `EducationalProgram`.
- `EducationalProgram` включает профиль, кафедру и год набора.

### Дисциплины и компетенции
- `Discipline` — общий справочник.
- `ProgramDiscipline` — дисциплина в контексте конкретной программы.
- `Competence` — компетенция конкретной программы.
- `DisciplineCompetence` — матрица связи «дисциплина учебного плана -> компетенция».

### Задания
- `AssessmentItem`:
  - `program_discipline` (обязательная привязка к дисциплине учебного плана);
  - `competence` (одна компетенция на задание);
  - `assessment_item_type`;
  - текст задания и заголовки колонок для matching.
- `AssessmentItemRow` — универсальная строка задания:
  - `left_text`, `right_text`, `open_answer_text`, `is_correct`, `correct_order`, `sort_order`;
  - интерпретация зависит от типа задания.

> Почему `assessment_item` связан с `program_discipline`: потому что одна и та же дисциплина в разных программах — это разные контексты компетенций и покрытия.

## 10. Как устроена работа с заданиями
- Создание/редактирование: [assessment/forms.py](assessment/forms.py) + inline formset строк.
- Серверная валидация по типу задания:
  - один выбор: минимум 2 варианта, ровно 1 верный;
  - множественный выбор: минимум 2 варианта, минимум 1 верный;
  - соответствие: минимум одна пара; допускаются правые дистракторы;
  - последовательность: минимум 2 шага, `correct_order` задается автоматически;
  - открытый: минимум один допустимый ответ.
- На форме задания выбор компетенции ограничивается связями `DisciplineCompetence`.
- Список заданий поддерживает фильтры по уровню/направлению/профилю/программе/дисциплине/типу/компетенции + поиск по тексту.

## 11. Как устроена работа с компетенциями и дисциплинами
- Дисциплины:
  - отдельный справочник `Discipline`;
  - отдельный экран управления дисциплинами конкретной программы (`ProgramDisciplineManagerView`).
- Компетенции:
  - создаются в контексте конкретной образовательной программы;
  - связываются с дисциплинами учебного плана через `DisciplineCompetence`.
- Выбор допустимых компетенций для задания:
  1. выбирается `ProgramDiscipline`;
  2. показываются только компетенции программы;
  3. дополнительно фильтруются по наличию связи в матрице `DisciplineCompetence` (`linked_only`).

## 12. Как устроен экспорт в Word
- Точка входа: `/export/word/`.
- Сервис: [export/services.py](export/services.py), функция `generate_docx(program_id, discipline_id, filters)`.
- Экспорт:
  - берет задания по выбранной программе/дисциплине (и доп. фильтрам);
  - строит документ на базе `maket.docx`;
  - рендерит 3 раздела: спецификация, задания, ключи/критерии;
  - учитывает логику типов задания;
  - выполняет рандомизацию для вариантов/последовательности/правого столбца соответствия;
  - ключи рассчитываются по фактическому порядку в документе.

## 13. Как устроены отчеты
Раздел `/reports/` формирует таблицы по фильтрам:
- покрытие компетенций заданиями по программе;
- дисциплина -> компетенция -> количество заданий;
- количество заданий по типам;
- количество заданий по программам;
- количество заданий по дисциплинам.

Реализация: `annotate`, `Count`, `Q`, `F` в [reports/views.py](reports/views.py).

## 14. Пользовательский интерфейс
- Главная: `/` (карточки разделов + статистика).
- Основные рабочие экраны доступны через верхнюю навигацию.
- Формы ориентированы на ввод через сайт, не только через админку.
- Для длинных справочников реализован autocomplete:
  - backend: `/core/lookup/`;
  - frontend: JS в `templates/base.html`.
- Есть фильтрация, поиск и пагинация (в generic-списках через `NamedListView`).

## 15. Django admin
Админка настроена во всех рабочих приложениях:
- `list_display`, `search_fields`, `list_filter`;
- inline для `AssessmentItemRow` в заданиях;
- пригодна для сопровождения, но основной пользовательский поток реализован в веб-интерфейсе.

## 19. Применение миграций / работа с уже существующей БД
- Предметные модели проекта объявлены как `managed = False` и соответствуют уже существующей БД.
- Таблицы предметной области должны быть созданы SQL-скриптом вне Django миграций.
- Миграции Django используются только для стандартных служебных приложений (`auth`, `admin`, `sessions`), если их таблицы отсутствуют.

## 20. Начальные данные / справочники
Команда:
```bash
python manage.py seed_initial_data
```
Заполняет:
- уровни образования;
- типы компетенций;
- типы заданий;
- ученые степени/звания.

## 21. Примеры основных пользовательских сценариев
1. **Подготовка структуры ОПОП**
   - создать направление -> профиль -> образовательную программу;
   - привязать кафедру.
2. **Заполнение дисциплин и компетенций**
   - добавить дисциплины в учебный план программы;
   - создать компетенции программы;
   - связать дисциплины и компетенции через матрицу.
3. **Создание задания**
   - выбрать `program_discipline`, тип задания, компетенцию;
   - заполнить строки задания согласно типу;
   - сохранить и проверить в карточке.
4. **Формирование отчетов**
   - открыть `/reports/`, выставить фильтры, анализировать покрытие.
5. **Экспорт в Word**
   - открыть `/export/word/`, выбрать программу/дисциплину, скачать `.docx`.
6. **Импорт программы из PLX**
   - открыть `/programs/`, загрузить `.plx`;
   - при конфликте подтвердить замену или отменить.

## 23. Текущее состояние проекта, известные ограничения и что можно улучшить
### Реализовано
- сквозной пользовательский UI по основным сущностям;
- валидация заданий и связей дисциплина/компетенция;
- отчеты и экспорт Word;
- импорт `.plx` с безопасной заменой существующей программы.

### Реализовано частично / ограничения
- автоматизированные тесты по бизнес-логике фактически отсутствуют (`assessment_app/tests.py` — заглушка);
- приложение `assessment_app` присутствует как неиспользуемый каркас и не подключено в `INSTALLED_APPS`;
- `reports/models.py` и `export/models.py` — пустые заглушки (логика вынесена в `views/forms/services`);
- в репозитории есть служебный/резервный файл `assessment_rinh/settings.py~`;
- `templates/disciplines/detail.html` не задействован текущими `urls/views` и выглядит устаревшим;
- `seed_initial_data` использует укороченные названия типов заданий, тогда как UI рассчитан и на полные русские формулировки (сопоставление выполняется по эвристике в `assessment/services.py`);
- `ALLOWED_HOSTS = ['*']` и `DEBUG = True` в `settings.py` — приемлемо для разработки, но не для production.

### Рекомендации по доработке
- добавить тесты сервисов (`programs/services`, `assessment/forms`, `export/services`);
- вынести/убрать неиспользуемые модули и артефакты;
- унифицировать справочник типов заданий и команду инициализации;
- усилить production-конфигурацию (`DEBUG`, `ALLOWED_HOSTS`, секреты, static/media);
- при необходимости разделить большой `export/services.py` на меньшие компоненты.

## 24. Итог
Проект уже представляет собой рабочую методическую систему, где данные связаны с реальной структурой образовательных программ, а не с абстрактным банком тестов.  
Основной пользовательский контур реализован через веб-интерфейс, поддерживает ввод, проверку связей, анализ и печатный вывод. Ключевые зоны роста — автотесты, очистка наследованных артефактов и окончательная унификация справочников типов заданий.
